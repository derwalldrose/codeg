# Web Runtime Shell 改动说明

本文档说明 `feat/web-runtime-shell` 分支当前已完成的改动、能力边界，以及后续计划。

## 本次改动目标

本次改动的目标不是一次性把整个桌面应用完整迁移成 Web 全栈，而是先把前端从“必须由 Tauri 宿主启动”调整为“可以脱离 Tauri 直接以普通 Web 页面方式运行”。

这一步的重点是：

- 保留现有 `Tauri + Next.js` 结构，避免一次性删除桌面能力
- 抽离前端对 Tauri 运行时的直接耦合
- 让欢迎页、设置页、文件夹页等核心 UI 在浏览器里先跑起来
- 为后续逐步把 Tauri command 迁移为真实 Web API 留出稳定入口

## 已完成改动

### 1. 新增统一运行时适配层

新增 `src/lib/runtime.ts`，把以下能力统一封装：

- 运行时识别：区分当前是 `Tauri` 还是普通 `Web`
- 事件监听
- 文件/目录选择
- 外链打开
- 文件管理器中定位文件
- 窗口控制与关闭行为

这样前端业务代码不再需要在组件里直接依赖 `@tauri-apps/*`。

### 2. `src/lib/tauri.ts` 支持 Web fallback

原本 `src/lib/tauri.ts` 只负责透传 Tauri `invoke()`。

现在改成：

- 在 Tauri 环境中，继续走原生 `invoke()`
- 在 Web 环境中，走最小可运行 fallback
- 对暂不支持的桌面能力，返回明确的降级行为或提示

当前 Web fallback 主要提供：

- 欢迎页历史列表的最小 demo 数据
- 文件夹页可进入的默认工作区壳
- 设置页、提交页、欢迎页等页面跳转能力
- 语言设置、部分列表接口的基础兜底返回

### 3. 移除前端对 Tauri API 的硬绑定

已把下列能力改成走运行时适配：

- 欢迎页打开文件夹
- 文件夹切换
- 分支面板中的目录选择与事件监听
- 命令下拉中的终端退出监听
- 文件树与 Git 变更面板中的事件监听
- 消息输入框中的附件选择
- 状态栏中的外链打开
- 设置页中的外部链接跳转
- 提交页中的窗口关闭
- ACP 连接事件监听
- 终端面板事件订阅

### 4. 标题栏与窗口控件做了运行时隔离

Web 模式下不再显示仅桌面版才有意义的 Windows 原生窗口按钮，避免用户在浏览器里看到无法工作的桌面控件。

### 5. 调整开发与构建脚本

由于当前仓库在 `Next 16 + next-intl` 组合下，`Turbopack` 路径会触发 ESM `require()` 相关构建问题，因此：

- `dev` 改为 `next dev --webpack`
- `build` 改为 `next build --webpack`

这样开发和生产构建都可直接跑通。

## 当前效果

当前分支已经实现：

- `pnpm dev` 可以直接启动 Web 前端
- `pnpm build` 可以完成静态构建
- 项目不再必须依赖 Tauri 宿主才能打开页面

当前分支尚未实现：

- 自动启动真实后端服务
- 把 Rust/Tauri command 全量迁移成 HTTP API
- 在 Web 模式下完整支持本地文件系统、终端、Git、ACP 等全部能力

## 当前能力边界

这个分支目前属于“Web 可运行壳层”阶段，而不是“完整 Web 全栈版本”。

也就是说：

- 页面已经能在浏览器中独立运行
- 但桌面专属能力大多还是 fallback、占位数据或明确提示
- 真正的后端能力还没有完全从 Tauri command 迁移到 Web API

## 本地开发方式

### Web 前端开发

```bash
pnpm install
pnpm dev
```

启动后访问：

```text
http://localhost:3000
```

### Web 构建

```bash
pnpm build
```

构建产物输出到：

```text
out/
```

### 桌面开发

如果仍需验证原 Tauri 桌面壳，可继续使用：

```bash
pnpm tauri dev
```

## 后续改动计划

后续建议按以下顺序推进。

### 第一阶段：把关键 fallback 替换成真实 Web API

优先迁移这些能力：

- 文件夹列表与会话列表读取
- 设置页基础数据读取
- 目录详情与文件树读取
- 基础 Git 状态读取

目标是让欢迎页、文件夹页和设置页先从 demo/fallback 切到真实服务端数据。

### 第二阶段：补齐 Web 后端运行时

把当前 Tauri command 逐步改造为可供 Web 调用的服务接口，候选实现包括：

- Next.js Route Handlers
- 单独 Node 服务
- 独立 Rust HTTP 服务

这一阶段完成后，Web 模式才算具备“真实后端”。

### 第三阶段：拆分桌面专属能力与 Web 能力

把以下能力做进一步隔离：

- 窗口管理
- 原生文件对话框
- Tauri 事件流
- 原生终端

目标是让 Web 与桌面共用业务 UI，但分别使用自己的 runtime adapter。

### 第四阶段：迁移终端、Git 与文件编辑链路

按价值优先级逐步推进：

1. 文件树与只读预览
2. Git 状态与 Diff
3. 文件编辑与保存
4. 终端与命令执行

### 第五阶段：迁移 ACP 实时连接能力

这部分复杂度最高，后续需要评估：

- WebSocket 代理
- 服务端会话管理
- 权限请求与流式事件桥接

这一阶段完成后，Web 版才会真正接近桌面版的会话交互能力。

### 第六阶段：再决定工程形态

等 Web 后端路径稳定后，再决定是否：

- 继续保留 `src-tauri/` 与 Web 兼容共存
- 拆分为 `desktop` / `web` 双入口
- 或进一步收敛项目结构

## 总结

这次分支完成的是第一步：把项目变成“前端可脱离 Tauri 独立运行”的状态。

下一步真正要做的，是把当前的运行时 fallback 逐步替换为真实 Web 后端和真实接口能力，让它从“能打开的 Web 壳”演进到“可实际使用的 Web 版本”。
